## SEC-01 — Medium: existing disabled-account sessions retain native auth access

**Confirmed at baseline; remediated in this branch.** Application authentication
already checked `user.disabled` in [utils/auth.ts](../../backend/src/utils/auth.ts).
Native auth requests previously reached Better Auth without this check, and the
session-creation hook did not revoke existing sessions.

Local production-mode D1 reproduction, using the same session before/after
disabling its owner:

- `GET /api/users/stats`: **403**, with both bearer and signed secure cookie.
- `POST /api/auth/update-user`: **200**, with both bearer and signed secure cookie.
- D1 confirms the disabled user's name changed. Attempting `disabled:false` in
  that request leaves the protected disabled flag set.

Requires an existing, unexpired session. No access to another account or ability
to re-enable the account was demonstrated. The audited source matches the observed
production build at baseline; authenticated exploitation was tested only against fixtures.

**Implemented remediation:** [native auth dispatch](../../backend/src/auth/handler.ts)
validates cookies/bearer sessions through Better Auth, rejects disabled owners
and revokes their sessions. Trusted sign-out remains available; signed dashboard
requests keep their independent authentication. Origin checks reject untrusted
writes before revocation. [Auth user-update hooks](../../backend/src/init/auth.ts)
also await revocation when a user is disabled, including updates outside an HTTP
endpoint. Re-enabling does not restore revoked sessions. Direct SQL edits bypass
update hooks; existing/directly disabled accounts are checked at native dispatch.

Evidence: [baseline results](account-controls-2026-10-22.json),
[fixed results](account-controls-fixed-2026-10-22.json),
[current regression source](reproduce-account-controls.mts).
Both native mutation paths now return **403**, leave the name/disabled flag
unchanged, and leave **zero sessions** for the disabled fixture owner.
The same reproduction confirms retired API-key creation returns **404**,
`ApeKey` authentication returns **401**, and stale-session username changes
return **401**. Earlier SEC-02/SEC-03 remain resolved by API-key removal.

## SEC-04 — Development dependencies: critical and high advisories remain

**Installed affected versions confirmed; exploitation was not attempted.**
These affect developer/tooling contexts. No production website request path to
the affected tooling was identified. Developer compromise can still threaten
source code and credentials.

- **Critical:** `storybook@10.6.1` and `@storybook/addon-vitest@10.6.1`.
  [The addon is enabled](../../frontend/storybook/.storybook/main.ts#L67).
  A malicious website can affect a browser-opened vulnerable Storybook dev
  server, potentially changing project files and, under further conditions,
  executing code. Upgrade the Storybook packages together to **10.6.2 or newer**
  before launching the dev server again. Static built Storybooks are outside
  this advisory's affected context.
  [Maintainer advisory](https://github.com/storybookjs/storybook/security/advisories/GHSA-f2ph-cmg5-wxc8).
- **Moderate/high:** `vite-plus@1.0.0` includes editor execution/file-disclosure
  advisories and the Vitest file-deny issue. The refreshed scan requires
  **Vite+ 1.3.0 or newer** to address all currently listed entries; upgrading only
  to 1.1.0 no longer covers the whole set. Update its Vite alias and the
  [workspace catalog/overrides](../../pnpm-workspace.yaml) together.
  [Editor advisory](https://github.com/vitejs/launch-editor/security/advisories/GHSA-587h-7wmj-h5pm),
  [Vitest advisory](https://github.com/vitest-dev/vitest/security/advisories/GHSA-p458-7748-mcp3).
- **Moderate:** `@vitest/browser` and `@vitest/ui` at **5.0.3** also carry that
  file-deny advisory; update the coordinated Vitest packages to **5.0.5 or newer**.
  It requires an HTTP-serving UI, browser or API mode; the ordinary non-browser
  `vp test run` executions used here do not enable that server.
  [Maintainer applicability](https://github.com/vitest-dev/vitest/security/advisories/GHSA-p458-7748-mcp3).
- **High/moderate/low:** `undici@7.29.0`, through
  `frontend > @cloudflare/vite-plugin > miniflare`, has ten entries. Upgrade its
  compatible parent dependencies to resolve to **7.29.1 or newer** on the 7.x
  line. Actual exposure depends on using affected clients/interceptors with
  hostile responses. Cloudflare production fetch uses its runtime implementation.
  [Maintainer example](https://github.com/nodejs/undici/security/advisories/GHSA-rfgv-xxqx-mfg5).
- **High:** `braces@3.0.3`, through analysis/style tooling, has a recursive-pattern
  denial of service advisory. Registry audit lists **no patched release**.
  Track upstream and constrain untrusted glob inputs; no blanket audit ignore.
  [Advisory](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm).

## Additional hardening

- **OAuth token storage:** encryption remains unset in
  [account configuration](../../backend/src/init/auth.ts#L88).
  Installed Better Auth 1.7.7's `dist/oauth2/utils.mjs` encrypts stored provider
  tokens only with `account.encryptOAuthTokens`. The fixture confirms a plaintext
  token written through the internal adapter; it is not a production token read
  or an end-to-end OAuth storage test. Enable supported encryption with migration,
  key-rotation and rollback handling, or stop retaining unnecessary tokens.
- **Hosted dev mode:** [default Wrangler config](../../frontend/wrangler.jsonc)
  combines `workers_dev:true`, `MODE:dev` and the staging D1 binding. Dev mode
  intentionally permits caller-selected `Uid` authentication and public
  configuration editing. This becomes a serious authorization bypass if deployed
  publicly with data. No such deployment was established. Make the local config
  non-public and reject hosted dev mode; release configs already use production mode.
- **Continuous checks:** reviewed CI has no explicit dependency-advisory or
  secret-scanning job. Add recurring scans, reviewed exceptions for unpatched
  tooling, and SHA-pinned third-party Actions. GitHub account-level protections
  were not inspected. Historical dependency-audit counts are snapshots.

**286 tests passed across 31 files**, with no failures:

- Backend auth/dashboard, authentication/permission policies, HTTP protocol,
  D1 authentication/privacy/ownership, service boundaries: **106 tests, 9 files**.
- Captcha, result validation/client isolation, service-worker cache policy:
  **66 tests, 4 files**.
- Preset controller: **17 tests, 1 file**.
- Full built Start SSR/Worker/import/bundle suite: **97 tests, 17 files**.

Checks cover revoked/expired sessions, foreign-origin requests, admin/owner
permissions, response/error boundaries, request/decompression limits, nonce CSP,
static fallbacks, runtime isolation, and retired key routes. Passing existing
tests does not cover the disabled-account gap; the separate reproduction proves it.
The updated reproduction passes type-aware lint/type checking.

Eight read-only production GETs verified headers and anonymous access:
`/`, `/login`, `/privacy-policy.html` return **200**; `/api/users` and `/api/admin`
return **401**; `/api/configure` returns **404**. Dynamic responses carry nonce
CSP, HSTS, nosniff, SAMEORIGIN, same-origin referrer policy and no-store.
Static `/sw.js` and `/version.json` return **200**, no-cache, and bypass the
Worker response headers. No exploit is inferred solely from these absent static
headers. [Captured responses](production-headers-2026-10-22.json).

Reviewed SQL uses bound caller values; dynamic table names reviewed are closed
internal choices. Private result/preset/config access uses authenticated owners.
Reviewed HTML injection sites render fixed bootstrap/fallback content; OAuth
popup messaging checks origin, window source and request ID. These are bounded
review findings, not proof that injection is impossible everywhere.

A credential-pattern scan covered **2,801 text files / 3,004 tracked files**,
with no matches for the five recorded credential/key formats. It does not detect
all secret types. [Scope/results](secret-pattern-scan-2026-10-22.json).

## SEC-01 remediation verification

After the fix, the complete backend suite passes **787 tests / 63 files**, and
the complete built Start suite passes **99 tests / 17 files**: **886 tests total**.
Both standard/runtime-test builds, repository-wide type-aware lint/type checking,
and the standalone regression pass.

New tests cover native reads/writes with cookies and originless bearer tokens,
all-session revocation without affecting another user, enabled-account updates,
sign-out, foreign-origin rejection before revocation, signed dashboard access,
revocation through D1 update hooks, new-session rejection while disabled,
re-enabling with a new session, and built Worker/UI session behavior.
The six initial native-access cases failed with **200** before the fix and pass
with **403** afterward. Revoked credentials subsequently return **401** on
protected operations.

No schema migration is required. Existing disabled accounts are checked on their
next native auth request; hook-based disabling revokes sessions immediately.
Production was not deployed or mutated during remediation. The captured
production headers and original finding describe the pre-fix deployment.
