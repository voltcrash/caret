### F01 — High: five settings freeze the browser when submitted

Affected settings:

| Control | Reproduction | Source |
| --- | --- | --- |
| Minimum speed | `/settings?highlight=minSpeed`; change to `80`; Tab away | [MinSpeed.tsx:58](../../frontend/src/ts/components/pages/settings/custom-setting/MinSpeed.tsx#L58) |
| Minimum accuracy | `/settings?highlight=minAcc`; change to `95`; Tab away | [MinAcc.tsx:56](../../frontend/src/ts/components/pages/settings/custom-setting/MinAcc.tsx#L56) |
| Minimum burst | `/settings?highlight=minBurst`; change to `75`; Tab away | [MinBurst.tsx:58](../../frontend/src/ts/components/pages/settings/custom-setting/MinBurst.tsx#L58) |
| Background URL | `/settings?highlight=customBackground`; enter a valid HTTPS `.png` URL; Enter | [CustomBackground.tsx:152](../../frontend/src/ts/components/pages/settings/custom-setting/CustomBackground.tsx#L152) |
| Animation FPS | `/settings?highlight=animationFpsLimit`; change to `30`; Tab away | [AnimationFpsLimit.tsx:74](../../frontend/src/ts/components/pages/settings/custom-setting/AnimationFpsLimit.tsx#L74) |

Expected: save valid input, update the setting and leave the page responsive. Actual: input submission stalls and the renderer stops responding. Four independent targeted tests failed, followed by a separate FPS reproduction. The earlier ordinary browser attempts also stalled before debugger instrumentation was introduced.

The five components call `form.handleSubmit()` from `validators.onBlur`. Submission runs validation again, re-entering submit. Debugger samples from every affected control show the page inside TanStack Form validation/store notification or `_handleSubmit`. This is more than a slow test or a failed persistence assertion: keyboard actions time out while the page is stuck. The audit watchdog interrupted execution only after recording the stuck stack.

Fix direction: move submit-on-blur behavior into `listeners.onBlur`; keep validators pure. The existing [PaceCaret](../../frontend/src/ts/components/pages/settings/custom-setting/PaceCaret.tsx#L63), [MaxLineWidth](../../frontend/src/ts/components/pages/settings/custom-setting/MaxLineWidth.tsx#L45) and automatic settings controls already use that separation and pass browser checks. Add real-browser blur/Enter cases for all five controls.

Evidence: `freeze-browser.log`, `freeze-browser-results.json`, `fps-browser.log`, `fps-browser-results.json`, `freeze-{minSpeed,minAcc,minBurst,customBackground,animationFpsLimit}.json`, plus `freeze-traces/` and `fps-traces/`.

### F02 — Medium: Poetry and Wikipedia funboxes are blocked by CSP

Reproduction: load a words test with `funbox: ["poetry"]` or `["wikipedia"]`, or select the corresponding funbox through settings.

Expected: fetch and display the selected content. Actual:

- Poetry: `https://poetrydb.org/random` is blocked; an error appears, the funbox is cleared and ordinary words load.
- Wikipedia: `https://en.wikipedia.org/api/rest_v1/page/random/summary` is blocked; test initialization fails with `TypeError: Failed to fetch`.

[response-policy.server.ts:44](../../frontend/src/server/response-policy.server.ts#L44) permits only the application origin, Turnstile and optional Sentry in `connect-src`. It omits both supported content services. The browser reports explicit `connect-src` violations before any request reaches the fixture handler. With CSP bypassed and otherwise identical fixture responses, both funboxes initialize and remain selected. This isolates the application policy from third-party availability or CORS.

Fix direction: permit the required PoetryDB and language-specific Wikipedia connections, or fetch this content through an appropriate application endpoint. Preserve the remaining CSP restrictions. Add browser cases that keep production CSP enabled.

Evidence: `csp-poetry-false.json`, `csp-wikipedia-false.json`, matching `*-true.json` controls, screenshots and `csp-browser.log`. Here `false` means CSP enforced; `true` means CSP bypassed solely for diagnosis.

### F03 — Medium: valid remote background URLs cannot display

Reproduction: import or restore `customBackground: "https://example.test/background.png"` with a valid image supplied at that URL. Import avoids F01's separately broken URL form.

Expected: display the image. Actual: the value persists, but the image is hidden and the UI says its link is unavailable or expired. No image request reaches the supplied fixture.

[response-policy.server.ts:43](../../frontend/src/server/response-policy.server.ts#L43) at baseline allowed only `'self' data:` in `img-src`, while the setting schema accepts HTTP/HTTPS image URLs. The same image rendered with CSP bypassed. Local uploaded images worked because they use allowed data URLs. Evidence correction: the original `csp-background-false.json` captured an unrelated script-evaluation policy event, not an `img-src` event. The committed regression now explicitly observes an `img-src` console error for the blocked image and verifies the policy-specific notice in Chromium.

Fix direction: align the image policy with the advertised remote-background feature. Also distinguish a policy rejection from an expired image in the failure notice. Add a production-CSP browser test.

Evidence: `csp-background-false.json`, `csp-background-true.json`, corresponding screenshots, `csp-browser.log`.

### O01 — Low, internal hardening: malformed direct setter inputs can throw

The headless `resolveConfigChange` API throws for 16 deliberately mistyped calls involving `funbox`, `customLayoutfluid`, `customPolyglot`, `customBackground`, `customThemeColors` and `accountChart`. Overrides/block checks access `.trim()`, `.every()`, `.length` or indexes before schema validation. Example: `resolveConfigChange("customBackground", null, defaults)` throws instead of returning an invalid result.

These calls violate the TypeScript parameter contract. **No user-facing import failure was demonstrated.** All 2,434 import-resolution probes passed, and browser imports safely repaired malformed values. Treat this as an optional public-library boundary hardening opportunity, not another confirmed UI defect. Evidence: `config-results.json`, `config-audit.log`.

## Coverage boundaries

- There is no single complete, current product spec in the checkout. Current schemas, option descriptions, routes, architecture/development docs and tests were the oracle. Historical migration docs explicitly describe removed features and were not treated as current requirements.
- All 95 config keys were inventoried and probed. Every finite visible scalar option returned by shared metadata was included in the core sweep; arrays, strings and numeric domains received representative valid/invalid/boundary samples. Exhausting arbitrary text, numeric values, network states and every combination of settings is unbounded.
- Actual Firefox, Safari/WebKit, physical touch keyboards, OS input methods, speech voices, speakers and screen-reader sessions remain unverified. Browser accessibility checks are automated Chromium checks.
- Real hosted OAuth/Turnstile, production credentials, Cloudflare remote services, live third-party availability, external quote-approval integration and live production load were not exercised. Public test keys and local fixtures were used for build/runtime checks.
- Tags, presets, profile/account maintenance, quote moderation, API-key administration and server configuration have unit/service/D1 coverage; this audit did not click through every authenticated administrative form against a real hosted account.
- The preview tool twice timed out taking a snapshot. Browser work continued through the repository's documented Playwright workflow. This is tooling, not an Oxytype finding.
- Builds emit a CSS sourcemap warning and Madge import-resolution warnings, while compilation and the circular-import check succeed. Those warnings were not demonstrated to affect product behavior.
