## Confirmed findings

### SEC-01 — Medium: disabled accounts retain access to native auth operations

Evidence: [auth dispatch](https://github.com/voltcrash/oxytype/blob/c1da7433a108c6693c8585616ef1e9d80901fe10/backend/src/auth/handler.ts#L29),
[auth hooks](https://github.com/voltcrash/oxytype/blob/c1da7433a108c6693c8585616ef1e9d80901fe10/backend/src/init/auth.ts#L110),
[application session check](https://github.com/voltcrash/oxytype/blob/c1da7433a108c6693c8585616ef1e9d80901fe10/backend/src/utils/auth.ts#L10).

`verifySession()` rejects `auth_users.disabled=true`, and the session-creation
hook rejects new sessions. Native Better Auth routes go directly to
`auth.handler()`, which does not enforce this custom field on existing sessions.

Local production-mode reproduction: create a session, disable its owner, then
use the same bearer token. `GET /api/users/stats` returns **403**, while
`POST /api/auth/update-user` with `{ "name": "Disabled account mutation" }`
returns **200**. Requires an existing, unexpired session; does not permit changing
another user's account or clearing the protected `disabled` field.

Impact: disabling an account does not consistently terminate its authenticated
capabilities. This auth path remains available with API keys disabled.

Fix: enforce disabled status for authenticated native auth operations through a
shared hook, and revoke existing sessions when disabling. Preserve sign-out and
the independently authenticated dashboard's administration flow. Test both
cookie and bearer sessions against native auth and application routes.

### SEC-02 — Medium, conditional: API keys ignore disabled-account status

Evidence: [API-key authentication](https://github.com/voltcrash/oxytype/blob/c1da7433a108c6693c8585616ef1e9d80901fe10/backend/src/policies/authentication.ts#L125).

The key path checks its hash and `enabled` flag, but never checks its owner's
authentication account. Local reproduction: after disabling the owner, session
access to `/api/users/stats` returns **403**; its existing API key returns **200**.

Impact: a retained/stolen key can continue reading the account's API-accessible
data after the account is disabled. Keys have no expiration field. This is
distinct from `users.banned`, which also serves leaderboard moderation rules.

Production currently reports `apeKeys.acceptKeys=false` and
`apeKeys.endpointsEnabled=false`; the private API-key path is therefore gated
off. Fix before enabling it: check that the authentication owner exists and is
enabled on every key-authenticated request, and revoke keys when disabling.
Test missing owners, disabled owners, disabled keys, and re-enabled accounts.

### SEC-03 — Medium, conditional: stale sessions can create persistent API keys

Evidence: [key creation metadata](https://github.com/voltcrash/oxytype/blob/c1da7433a108c6693c8585616ef1e9d80901fe10/packages/contracts/src/ape-keys.ts#L54),
[freshness enforcement](https://github.com/voltcrash/oxytype/blob/c1da7433a108c6693c8585616ef1e9d80901fe10/backend/src/policies/authentication.ts#L106),
[session revocation](https://github.com/voltcrash/oxytype/blob/c1da7433a108c6693c8585616ef1e9d80901fe10/backend/src/utils/auth.ts#L41).

Key creation and modification omit `requireFreshToken`. A five-minute-old
session creates a key with **200**, while username changes using the same
session return **401** for failing the one-minute reauthentication requirement.

Impact: someone holding a stolen session can create a durable second credential.
Revoking sessions does not delete API keys. This is an escalation in persistence,
not an unauthenticated attack; API keys are currently disabled in production.

Fix: require fresh authentication for key creation and re-enabling keys, with
matching UI reauthentication. Offer an explicit account-compromise recovery
action that revokes sessions and API keys. Keep session-only revocation clearly
labelled. Verify stale cookie and bearer sessions cannot mint/re-enable keys.

### SEC-04 — Development-tool dependency advisories

Registry audit: **4 high, 9 moderate, 4 low; 0 critical**. Production-only audit:
**0 known advisories**. These are advisory counts, not 17 proven attack paths.
Full results: [dependency evidence](dependency-audit-2026-10-21.json).

- `vite-plus@1.0.0`: six advisories; registry lists `>=1.1.0` as fixed. Includes
  editor command execution and dev-server file disclosure. The high-severity
  editor issue has Windows-specific prerequisites; it is not evidence of command
  execution in the deployed Cloudflare Worker.
  [Maintainer advisory](https://github.com/vitejs/launch-editor/security/advisories/GHSA-587h-7wmj-h5pm).
- `undici@7.29.0`, through `frontend > @cloudflare/vite-plugin > miniflare`: ten
  advisories; upgrade to a compatible patched version, at least `7.29.1` on the
  7.x line. These affect development tooling's network clients; production uses
  Cloudflare's runtime fetch. Actual exploitability depends on the affected API
  being used and attacker-controlled responses.
  [Maintainer advisory](https://github.com/nodejs/undici/security/advisories/GHSA-rfgv-xxqx-mfg5).
- `braces@3.0.3`, through lint/build tools: recursive-pattern denial of service;
  no patched version listed at audit time. No website-request path to this
  development dependency was identified. Track upstream; constrain untrusted
  patterns/tool inputs rather than inventing a patched version.
  [Affected recursive code](https://github.com/micromatch/braces/blob/3.0.3/lib/compile.js#L49-L53).

Upgrade the Vite+ toolchain/catalog and compatible Cloudflare dependencies
together, regenerate the lockfile, rerun audits, builds and security suites.
Avoid exposing development servers publicly. No dependencies were upgraded in
this audit.

## Additional hardening

- **OAuth token storage:** `account.encryptOAuthTokens` is unset in
  [auth configuration](https://github.com/voltcrash/oxytype/blob/c1da7433a108c6693c8585616ef1e9d80901fe10/backend/src/init/auth.ts#L88). Installed Better Auth
  1.7.7 encrypts provider tokens only when this option is enabled
  (`better-auth/dist/oauth2/utils.mjs`). Enable encryption with a migration and
  rollback plan for existing access/refresh/ID tokens; alternatively avoid
  retaining tokens the app does not need. This reduces the impact of database
  reads/backups leaking; no database compromise was demonstrated. The local
  fixture confirms plaintext storage, not access to production tokens.
- **Continuous detection:** checked-in CI runs quality/runtime checks but no
  explicit dependency-advisory or secret-scanning job. Add audit checks and
  scheduled detection, with reviewed exceptions for unreachable/unpatched
  development advisories. Pin third-party Actions to reviewed commit SHAs.
  Repository-level GitHub protections were not inspected.
- **Public development deployment:** default
  [Wrangler config](../../frontend/wrangler.jsonc) combines `MODE=dev`, a staging
  database binding, and `workers_dev=true`. Dev mode deliberately allows `Uid`
  authentication and public configuration editing. Production/staging release
  configs use production mode; no exposed dev deployment was established.
  Keep local config non-public and reject hosted dev-mode deployments.

## Controls verified

- Shared operation runner applies authentication, rate limits, permissions,
  configuration gates and contract validation across HTTP and server functions.
- Reviewed result/key/preset operations scope private data to the authenticated
  owner; SQL uses bound parameters. Targeted D1 ownership/privacy tests pass.
- Session revocation/expiry, last-provider protection, disabled new-session
  creation, production rejection of `Uid` auth, and foreign-origin write
  rejection pass targeted tests. The disabled-account gaps above remain.
- Request bodies and decompressed output are capped at 100 KiB. Malformed JSON,
  unsupported encodings and decompression bombs are covered by passing tests.
- Start's server/client import protections, browser bundle boundaries, error
  redaction, per-request runtime isolation and static fallbacks pass checks.
- Turnstile verifies success, expected hostname/action, and rejects production
  test secrets. OAuth popup messaging checks origin, source and request ID.
- Production responses for `/`, `/login`, `/privacy-policy.html` and protected
  API requests carry nonce CSP, HSTS, `nosniff`, framing protection and no-store.
  Anonymous `/api/users` and `/api/admin` return **401**; `/api/configure` is
  **404**. Static `/sw.js` and `/version.json` return **200**, `no-cache`, and
  bypass Worker response headers as configured. These were read-only checks.
- Pattern scan covered 3,008 tracked files. Flagged locations were documented
  placeholders or public development/test values; no live credential was
  identified by those patterns. Opaque secrets and Git history remain outside
  this heuristic check's assurance.

## Reproduction and validation

Install used the frozen lockfile with lifecycle scripts disabled. Both Start
builds succeeded. Ten targeted backend files passed **99 tests**. Nine distinct
Start test files passed: `document`, `http`, `bundle`, `import-protection`,
`services`, `operation-functions`, `auth`, `worker`, and `mutations`.
Initial missing `start-test` artifacts caused two test failures; building the
required runtime-test entry and rerunning those files resolved them.

Run the standalone account-control reproduction after installing dependencies:

```sh
vp -C backend exec tsx ../docs/security/reproduce-account-controls.mts
vp pm audit --json
vp pm audit -- --prod --json
```

The reproduction creates/disposes an isolated, migrated Miniflare D1 database,
uses production-mode shared HTTP/auth handlers, and prints only fixture results.
It verifies the retired key routes/headers and intentionally reproduces the
remaining native-auth disabled-account gap. It does not test Start routing or
production accounts; built-Worker regression tests cover the key removal.

## Remaining assurance gaps

No destructive production probes, load testing, authenticated production
penetration test, full browser attack campaign, historical secret scan, or
infrastructure-account review was performed. Cloudflare WAF/DDoS rules, D1
permissions/backups/restores, credential rotation, OAuth console settings,
dashboard authorization configuration, GitHub branch protection and incident
alerting need separate operational verification. External quote-publishing
bridge internals were unavailable.

Client-generated typing data cannot prove a human typed it; the unkeyed result
hash is not a signature. Existing [anticheat limits](../ANTICHEAT.md#limits-and-monitoring)
document this boundary. A clean advisory scan and passing tests do not eliminate
unknown vulnerabilities or guarantee leaderboard integrity.

Priority: fix disabled-account enforcement first, update vulnerable tooling,
close API-key persistence gaps before enabling keys, then harden token storage
and automate recurring checks.
